# 第三十八阶段：加载圈 + 无法拍照的真实失败链路（已抓到现场日志）

日期：2026-10-30 23:05–23:30
设备：TYH212U / Android 11
前置：第三十七阶段（已确认触发条件是"画面内容变动"，不是暗场景）

---

## 一、本轮最重要的产出：抓到了失败链路的现场日志

一次拍摄失败时，`ShotTracker` 打出了完整生命周期：

```text
E CAM_ShotTracker: Failed shot 1793372911514 detected. Log contents:
   {ShotId-0, 1793372911514, IMG_20261030_230831, HDR_PLUS, 27089, false, {}}
   HDR_PLUS started at 2026-10-30T15:08:31.534Z
   startEmpty
   Touched MediaFile-1
   onFramesRequested, isZsl=false, isFlashShot=false      ← 15:08:34.941
   marked failed                                          ← 15:08:38.142（3.2 秒后）

W CAM_lvs : [ShotId-0] Mediagroup.Listener#onAbandoned: PXL_20261030_150831514
E CAM_mjn : Error retrieving Gcam metadata.
            java.util.concurrent.TimeoutException: Waited 500 milliseconds
            for suu@e5f0850[status=PENDING]
E CAM_ShotTracker: showing "Possible shot loss" warning
```

### 1.1 这说明什么

| 环节 | 结果 |
|---|---|
| 按下快门 | 正常，shot 以 `HDR_PLUS` 启动 |
| 请求帧 | 正常（`onFramesRequested, isZsl=false`） |
| 取回 Gcam 元数据 | **失败**：等待 500ms 超时，future `suu` 始终 `PENDING` |
| 后果 | shot 被判 `marked failed` → `onAbandoned` → 弹出 "Possible shot loss" |
| UI 表现 | 取景框中间转圈（就是用户说的加载圈）+ 快门变灰、点击无响应 |

**这就是"一直加载 + 无法拍照"的直接机制**：不是 UI 状态机卡住，而是**拍摄流程在取元数据这一步失败**，GCam 把这张 shot 丢弃并把 UI 置为失败态。

### 1.2 相关类

- `suu`：`extends Lssf`，是一个 SettableFuture（有 `e(Object)` 完成、`a(Throwable)` 异常、`f(Lsui;)` 加监听）。
- `mjn.F`（类型 `Lsui;`）：这个 future 由 `mjn` 构造函数注入，`mjn.i(IJ)V` 里以 500ms 超时等待它。
- 超时后走 catch 分支打印 `Error retrieving Gcam metadata. %s`（`mjn.smali:4370`）。
- `CAM_ShotTracker` 判定失败并上报 "Possible shot loss"。

## 二、与已知证据的衔接

第三/八阶段曾记录：

```text
W libgcam [shot_process.cc:2485]: FinishShot: portrait_mask was invalid.
E libgcam [shot_process.cc:2490]: FinishShot: Failed to convert portrait_mask.
```

**推断（尚未直接证实，但链条自洽）**：原生 `FinishShot` 因 `portrait_mask` 转换失败而提前返回，导致本该回调给 Java 的 Gcam 元数据没有送出 → `suu` 永远 PENDING → 500ms 超时 → shot 失败。

即：**根因在原生侧，`portrait_mask` 是当前最可疑的断点。**

## 四、下一步（明确、可执行）

### 4.1 首选：验证 `portrait_mask` 是不是断点

1. 在失败时刻抓 `libgcam` 日志，确认 `FinishShot: Failed to convert portrait_mask` 与 `suu` 超时**同时出现**（本轮日志缓冲区滚动太快，两者没落在同一窗口，需一次干净的抓取）。
2. 若确认，方向是让 `FinishShot` 走成功分支：
   - 找到生成 portrait mask 的入口，喂一个"空但合法"的遮罩；
   - 或在模块里 hook 该转换，使其返回一个合法的空 mask。

### 4.2 次选：给 `suu` 兜底

如果原生侧短期修不了，可以在 `mjn.i(IJ)V` 的 catch 分支前给 future 一个兜底值，让 shot 至少能完成。
**风险**：元数据缺失可能导致出图异常（颜色/曝光/降噪参数缺失）。只能作为实验，不能当正式修复。

### 4.3 复现与判定口径

- 复现：正常启动 → 点快门 → 约 3 秒后应出现 `Failed shot` + `Error retrieving Gcam metadata`。
- 成功判据：**DCIM 新增 JPEG 且 `ShotTracker` 无 `Failed shot`**。
- 抓日志用 `adb logcat -d -t 3000`（本机 `-c` 清不干净，会混入旧记录，务必用 `-t` 限制行数）。

## 五、给接手者的一句话

**"一直加载、拍不了"的真身是 `suu` 这个 future 永远 PENDING**——`Error retrieving Gcam metadata: TimeoutException` 就是它。
往上游追，最可疑的断点是原生 `FinishShot: Failed to convert portrait_mask`。
别再在 UI 层（`setReadyState`、`ProgressOverlay`、`ShutterButton`）绕了，那些都是下游表现。

## 六、用户补充的关键信息与回归验证（23:20–23:30）

### 6.1 用户指出两点

1. 拍照后提示 **`Base frame index -1 is out of bounds [0,5]. Aborting capture processing.`**
2. **在交给本工作流之前（不是今晚），HDR+ 增强是能正常拍照的。**

这两条把方向钉死了：`Base frame -1` 表示**基准帧没选出来 → 整张被中止**，元数据自然不送出，于是 `suu` 永远 PENDING。而"以前能拍"说明这是**配置回归**，不是硬件死结。

### 6.2 对照交接文档，找到了回归源

交接文档（`01-交接给下一个LLM.md`）里写明：

> 正式六帧同曝光增强兼容路径：第二十六阶段两个会话 **6/6 + 2/2 保存并恢复快门**。
> 如需恢复已验证对照：`groupedexposure=0`、`burst.frames=6`、`uniformburst=1`、额外 probe 全 0。

而设备当时跑的是**第三十四阶段的实验配置**：`burst.frames=8` + `groupedexposure=1`（分组包围曝光）。这正是"以前能拍、现在不能"的差别。

### 6.3 回归验证结果

| 配置 | 结果 |
|---|---|
| `frames=8` + `groupedexposure=1`（实验配置） | **拍不了**：`Base frame index -1` → `Failed shot` → `Error retrieving Gcam metadata` 超时 → 转圈 + 快门灰 |
| `frames=6` + `groupedexposure=0` + `uniformburst=1`（第二十六阶段基线） | **拍成了**：DCIM 189→190，无 `Base frame`、无 `Failed shot`、无元数据超时 |
| `frames=4` + 同上 | **也拍成了**：DCIM 190→191，同样干净 |

日志佐证（基线配置）：

```text
TYH212U-HOOK: [uniform-burst] frames=6 exp_ms=40.0 gain=13.98
TYH212U-HOOK: [burst-limit] before builder max=-1 -> 6
TYH212U-HOOK: [burst-limit] begin shot=0 frames=6
```

### 6.4 结论

**HDR+ 增强拍摄能力没有坏，是第三十四阶段的分组曝光实验把它弄坏了。**
回到 6 帧同曝光（或 4 帧）即可恢复拍摄，与用户"以前能拍"的观察一致。

**注意**：模块里这三项的**代码默认值本来就是基线**（`frames` 默认 6、`uniformburst` 默认 1、`groupedexposure` 默认 0）。出问题是因为有人在运行期用 `setprop` 把设备切到了实验配置；`setprop` 重启后失效，所以**重启设备即可回到可用基线**。

### 6.5 仍未解决的部分

用户手动移动相机后，取景框出现灰环、快门变灰，**且此时日志里没有任何 `ShotTracker` / `Base frame` 记录**——说明这条"移动即卡"的路径**不是**拍摄失败引起的，与 6.3 的失败链路是**两回事**，尚未定位。

已知：
- 该状态**不会自愈**（观察 24 秒仍禁用）；
- 重启应用可恢复；
- 强制 `aeState=2`、点击画面对焦均无效；
- 该灰环**不是** `ProgressOverlay`（其方法从未被调用）。

下一轮应先确认它到底是 AF 搜索指示、还是别的等待态——建议 hook `ViewfinderCover`/焦点相关视图的可见性变化，或在灰环出现时抓一次完整的 `dumpsys activity top` 视图层级对比。
