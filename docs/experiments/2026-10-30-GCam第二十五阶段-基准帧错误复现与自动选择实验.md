# 第二十五阶段：基准帧错误复现与自动选择实验

2026-10-30，Asia/Shanghai。沿用 Google AWB=0，在新一轮日间曝光条件下关闭 CaptureAudit/InputSnapshot 诊断，正式候选首张即复现用户报告的基准帧错误：未保存照片，快门恢复，进程仍存活。前一夜成功组不能证明长期/跨光照稳定；也不能把本次失败直接归因于关闭诊断，因为场景和曝光条件已变化。

## 失败证据

6 帧逐个 nativeAddPayloadFrame 均 accepted=true，随后仍报 `ApplyBaseFrameOverride: Base frame override failed; specified base (0) was a dropped frame.`，再报 `Base frame index -1 is out of bounds [0, 5]`。**入口接受不等于帧通过所有后续原生检查**，因此修正此前以“全接受”推测没有丢弃的解释。

日志还记录 CheckRequestConsistency：首帧实际曝光 10 ms、请求 9.18098 ms；实际模拟增益 7.88×、请求 3.61601×；TET 超出请求。后续帧存在请求曝光/增益与实际结果相差一到数帧的现象。能确认基准帧 0 被丢弃且强制覆盖选择失败；曝光/增益不匹配是候选原因，不能断言是所有丢弃的唯一机制。

反编译 ila 的 ShotParams 构建路径会调用 `ShotParams_base_frame_override_index_set`，并存在 nonzsl_auto_base_frame_disable 配置分支。本次增加可回退的 BaseFrameRepair 实验：将显式非负基准帧覆盖改为 -1，交由原生选择存活帧；不改像素、曝光元数据、native 接收结果，也不将错误返回伪造成成功。

初始失败证据：`evidence/2026-10-30-stage25-initial-failed.json` 和 `stage25-initial-failed-native.txt`。原日志与单方法反编译在 `work/stage25/`。实验结果稍后追加。

## 自动基准帧实验结果

`baseframe-auto.json` 首张仍报 Base frame -1，中止且未保存。说明解除覆盖并不能补回被丢弃的帧，实验无效。其源码归档到 `work/stage25/experimental-src/`，不应作为默认修复。

## 一致曝光计划实验

由 BuildPayloadBurstSpec 输入的真实 FrameMetadata 读取当前实际曝光/模拟增益，使用原生 options 的 exposure_time_override_ms/gain_override，把短帧数量固定为 6、bracketing 数量设为 0。目标是避免短/长曝光交替造成的请求与实际值错位；保持真实结果元数据不变，不扩大原生容差、不绕过丢帧检查。此方案会减少增强模式的曝光包围能力，必须如实记录。

一致曝光审计组 3/3 保存且恢复快门，6 帧计划曝光均为 20 ms，模拟增益约 3.12–3.16×，实际帧报告曝光均为 20 ms。该组没有 CheckRequestConsistency 警告。恢复快门 10.74、8.77、8.87 秒。

随后保留 CaptureAudit、Google AWB=0 和其余配置，只关闭 uniformburst，单张对照再次复现第 0 帧被丢弃和 Base frame -1；请求曝光/增益再次交替，实际结果错位。该关闭对照说明此前成功不能简单归因于审计 Hook。

正式候选保留一致曝光计划，默认 `debug.gcam.fix.uniformburst=1`，仍受 `fix.burstlimit` 总开关控制。自动基准帧实验与单位矩阵颜色实验已移出正式源码。诊断 CaptureAudit/InputSnapshot 均默认关闭。

这支持“一致曝光计划避开当前 HAL 切换延迟引起的中止”的解释，不能证明所有未来 Base frame -1 都由同一原因导致。完整增强曝光包围尚未修复；本方案属于同曝光多帧的兼容路径。最终构建回归另见第二十六阶段。
