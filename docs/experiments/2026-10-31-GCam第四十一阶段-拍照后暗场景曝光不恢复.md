# 第四十一阶段：亮场景拍照后切到暗场景，取景框曝光不恢复（黑屏）

日期：2026-10-31 12:25–12:36（Asia/Shanghai）
设备：TYH212U / Android 11 / BSG MGC 9.6.080 V51
模块：临时探针 `AeProbe`、实验类 `AeRestartRepair`（默认关闭）

---

## 一、现象与复现

1. 对着明亮场景，点快门拍一张（HDR+ 走完、照片保存）；
2. 立即把手机对着暗处（桌下/遮光），取景框**保持全黑、不自动调曝光**；
3. 停着不动 20 秒以上仍不恢复；切换模式（夜视→照片）后立即恢复。

---

## 二、实测数据（AE 探针）

### 2.1 拍摄瞬间（正常）

```text
result aeState=3 (FLASH_REQUIRED)
result iso=50                      ← 亮场景已收敛到最低 ISO
result aeLock=true
request aeMode=0                   ← 拍照请求：AE 关闭（手动曝光，HDR+ 需要）
result aeMode=0 / aeState=0
request aeMode=1                   ← 拍完把 AE 模式改回 ON
result aeMode=1 / aeLock=false     ← 结果侧报告"已恢复自动"
```

### 2.2 之后（冻结）

- `result exposureNs` 与 `result iso` **不再变化**（例如停在 437976 ns、ISO 50）；
- 帧仍在出（`dumpsys media.camera` Frames produced 持续增长）；
- 取景框截图平均亮度 **1.2–1.4**（全黑）。

### 2.3 只有“会话重建”能恢复

切换夜视再切回照片（会重建相机会话）后：

```text
result exposureNs=30000500~40000000   ← 30–40 ms
result iso=423~564
截图平均亮度 98.4
```

结论：**HAL 的 AE 在“AE_MODE=OFF 的拍照请求”之后冻结在亮场景的曝光值**；
应用侧虽然把请求改回 AE_MODE_ON、结果侧也报告 aeMode=1/aeLock=false，但 HAL 的 AE 不再收敛，
只有重建相机会话（模式切换/重启应用）才能恢复。

---

## 三、试过但无效的修复

`AeRestartRepair`（实验，默认关闭）在“AE OFF→ON”之后向第一个 TEMPLATE_PREVIEW 请求注入：

1. `CONTROL_AE_PRECAPTURE_TRIGGER = START`
2. `CONTROL_MODE = AUTO`
3. `CONTROL_AE_LOCK = false`
4. `CONTROL_AE_MODE = ON`

日志确认注入成功（`request aePrecapture(req)=1` 等），但**暗场景取景框仍然全黑**，
曝光值没有任何变化——请求级“重启 AE”对这颗 HAL 无效。

---

## 四、下一步可选方案

1. **找到 GCam 内部的会话重建入口并调用**（模式切换就是走这条路径）：
   例如 `CameraDeviceManager`/`Camera2Session` 的重建/重启方法，在拍照完成后触发一次，
   这是最接近“切模式”效果的做法，但需确认不会丢帧或闪屏。
2. **UI 级自动模式切换兜底**：拍照完成后自动点一次“夜视→照片”（约 1–2 秒闪屏），
   行为稳定但用户可见；仅建议在“检测到拍摄后场景变暗”时触发。
3. **用户侧临时规避**：拍完照若换到暗场景，手动切一下模式（夜视→照片）即可恢复。
4. 若后续确认 HAL 在 `AE_MODE_OFF` 后需要 `CONTROL_AE_MODE=ON` 的**新会话**才能重新收敛，
   可研究在拍照结束后强制 `close/reopen` 相机（风险较高，需回归）。

## 六、会话重建路径的调查（12:36–12:38）

切模式时相机 **不关闭**：`dumpsys media.camera` 显示同一个 `CameraDevice` 保持 open，
只是输出流列表变化（2 条 → 1 条），说明是 **capture session 重建**。

挂 `CameraDeviceImpl.createCaptureSession`（多个重载）后抓到调用栈：

```text
createCaptureSession(SessionConfiguration)
  ← pmz.d ← prm.d ×4 ← pkj.a ← pli.b ← pli.e ← pkk.d ← pdy.d ← pen.a ← pep.m7ecc… ← pep.d …
```

这些 `pmz/prm/pkj/pli/pkk/pdy/pen/pep` 是 GCam 内部 Camera2 封装（混淆名），
参数包含 surfaces/session 配置，**无法安全地反射重放**：

- 直接调用 `createCaptureSession` 会与 App 自己持有的 session 冲突（同一 device 只能有一个活动 session）；
- 需要先关掉 App 的 session、再建新的，App 侧的 session 对象会失效，风险高。

结论：**“拍照后重建会话”在当前混淆结构下不可行**，可行的是“等价于用户切一次模式”的 UI 级动作。
