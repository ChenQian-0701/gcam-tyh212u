# GCam 第四阶段：重签名破坏原生层（决定性发现）

- 会话日期：2026-10-29（Asia/Shanghai），时段约 16:45–17:05
- 前置文档：《GCam适配工作记录.md》《2026-10-29-GCam续作-黑屏根因排查记录.md》《2026-10-29-GCam第三阶段-镜头死循环与取景器链路.md》
- 本次结论：**"改 DEX 再重签名"这条路线对本移植版根本不成立。** 只要 APK 被重签名，原生层就会失效（RamPatcher 运行时补丁不执行、`com.android.app.Application.o` 等 native 方法全部找不到实现），取景器因此永远拿不到可渲染的图像。这与我们改了哪些代码无关——**把原版 APK 原样重签名（零代码改动）就能复现**。

---

## 1. 一句话结论

原版 APK 的 `StartLibAddreses`（RamPatcher 运行时打补丁的痕迹）出现 3 次、`No implementation found` 0 次；**同一个文件只做重签名、一个字节代码都不改**，就变成 `StartLibAddreses` 0 次、`No implementation found` 2 次。

**签名本身就是这道开关。**

---

## 2. 三组对照实验

三组的安装流程完全一致：卸载 → 安装 → `pm grant` 五个权限 → 启动一次建目录 → `force-stop` → 写入同一份 27 项白名单 prefs → 启动抓 14 秒日志。

| # | 安装包 | 签名 | DEX 改动 | `StartLibAddreses` | `No implementation found` | `Cancelling viewfinder` |
| --- | --- | --- | --- | --- | --- | --- |
| A | `MGC_9.6.080_V51_MGC.apk`（BSG 原版） | BSG 原始 | 无 | **3** | **0** | 1 |
| B | 同上，仅用本地测试证书重签 | 本地测试证书 | **无** | **0** | **2** | 1 |
| C | `MGC_9.6_V51_TYH212U_test3.apk`（三处补丁） | 本地测试证书 | 3 处 | **0** | **29** | 0 |

A 与 B 的差异只有签名。B 与 C 的差异只有三处 DEX 补丁。结论：

1. 原生层失效的**唯一原因**是重签名（A→B）。
2. 我们的三处补丁是有效的——C 里 `Cancelling viewfinder` 消失，说明取景器创建事务的异常确实被修掉了。
3. 但 C 的 `No implementation found` 从 2 涨到 29，多出来的正是预览期间**逐帧**调用的 `com.android.app.Application.o`（YUV→RGB 转换，带色彩矩阵和色调曲线参数）。

## 3. 证据细节

### 3.1 原版（A）里的 RamPatcher 痕迹

```text
E StartLibAddreses: 7647f6c000      (×3)
E WARNING!!!: Cannot start the Google Camera App on an unsupported device
E HUAWEI_CAPTURE_RAW_STREAM_CONFIGURATIONS: Not Support ID = 0
```

`StartLibAddreses` 打印的是被 patch 的目标库基址，说明 `com.RamPatcher` 的 native 部分正常执行了。

### 3.2 原版重签名（B）里同一位置

```text
E oid.MGC_9_6_08: No implementation found for void com.RamPatcher.ReadyToPatch(java.lang.String)
E ERROR_METHOD: Lgzw;->a(Ljava/lang/Object;)V      (×2)
```

`StartLibAddreses` 一次都没有。RamPatcher 整条链路没跑起来。

### 3.3 三处补丁版（C）里逐帧失败

```text
E oid.MGC_9_6_08: No implementation found for java.nio.ByteBuffer
  com.android.app.Application.o(java.nio.ByteBuffer, java.nio.ByteBuffer,
  int, int, int, int, boolean, float[], int, float[], int, int, float[], int, float[])
```

该方法的签名是"两个 ByteBuffer（Y/UV 平面）+ 尺寸 + 布尔 + 四组 float 数组（色彩校正矩阵、色调曲线等）→ ByteBuffer"，正是**取景器每帧的 YUV→RGB 转换**。它拿不到实现，取景器就没有可显示的内容。

这与第三阶段的结论完全吻合：`viewfinder_frame` 是空的、`ViewfinderCover` 一直盖着、管线 `No outputSpecs` 从 `repeat=0` 起持续报错——**因为根本没有可渲染的输出**。

## 4. 机制推断（未完全证实，但与证据一致）

- 该 APK 带 `libpairipcore.so`（Play Integrity Protection），`assets/` 下有一个 39 MB 随机名加密载荷 `assets/QrQJbYT7…`。
- `com.RamPatcher` 与 `com.android.app.Application` 的 native 方法在 21 个 `.so` 里都找不到静态符号，也不含类名字符串——只可能由运行期注册（含 pairip 解密载荷后注册）。
- 重签名后这批注册整体失效，但主 DEX 的 Java 代码仍然正常跑（所以应用能启动、能开相机会话，只是原生层残缺）。

**未证实**：pairip 具体在哪一步拒绝注册；是否是校验 APK 摘要而非仅证书。

## 5. 对前面所有现象的统一解释

| 现象 | 新解释 |
| --- | --- |
| 取景器从未创建、`viewfinder_frame` 空、`ViewfinderCover` 常显 | 原生层 YUV→RGB 转换缺失，取景器无法建立，UI 一直处于"相机未就绪" |
| `No outputSpecs` 从 `repeat=0` 起 | 没有可渲染输出 → 管线没有输出规格 |
| 各种配置（白名单、Surface list、元数据开关、前后台）都不改善 | 与配置无关，缺的是原生能力 |
| 原版 APK 一装就崩 | 原版缺 `CONTROL_POST_RAW_SENSITIVITY_BOOST_RANGE` 处理，`loadConfinesExposureISO` 空指针 |
| 三处补丁版能跑但黑屏 | 补丁修掉了崩溃和死循环，但重签名把原生层一起废了 |

**换句话说：补丁和重签名是一对互斥条件——要修代码就必须重签名，重签名就废掉原生层。** 这就是这个移植版在本机上的死结。

## 6. 各版本可行性重新评估

| 版本 | pairip | 重打包是否安全 | 现状 |
| --- | --- | --- | --- |
| BSG 9.6 V51 | 有（`libpairipcore.so` + 39 MB 加密载荷） | **不安全**，重签名即废原生层 | 死结，只能走运行期 hook |
| BSG 8.1.101 GV2b | **无** | 安全 | 有纯 Java 签名自检（已补掉），之后卡在设备检测空指针 `nww.h` |
| 其他 8.x 移植版 | 多数无 | 待查 | 未测试 |

8.1 的签名自检位置与补丁：

- 类 `Landroid/support/v4/app/app/SignatureCheck;`
- 方法 `verifyIntegrity(Landroid/content/Context;)V`，CodeItem 偏移 **1630648**（`classes2.dex`），176 个 code unit
- 补丁：整段替换为 `return-void`（`0e00` + nop 填充），脚本 `tools/patch_81_sigcheck.py`
- 效果：`SignatureException: Apk signature is invalid` 消失，应用继续启动

随后 8.1 崩在设备检测：

```text
java.lang.RuntimeException: Unable to start activity ...
Caused by: NullPointerException: Attempt to invoke virtual method
  'java.lang.String java.lang.String.toUpperCase(java.util.Locale)' on a null object reference
  at nww.h(Unknown Source:617)
  at nww.a(Unknown Source:571)
  at nws.get / rlh.get / cym.get / rkz.get / cyl.get
```

`nww` 是 BSG 的设备识别/`device_key` 解析器（字符串常量含 `device_key`、`google`、`GENERIC`、`SDK_`、`unknown`、以及一段盐 `G1V5VHBME0Mq6trmUxb9Q9URJXm0Sof1|`）。它在 `CameraApp` 预创建阶段对某个空字符串做了 `toUpperCase`。**未修复**——该 APK 首次启动没有写出 prefs（只有 `reinit_prefs.ini`），无法用"预置 device_key"的方式绕过。

## 7. 运行期 hook：两条路与本机限制

既然重签名不可行，唯一出路是**不改 APK、在运行期修那三处**。本机条件：

| 条件 | 状态 |
| --- | --- |
| Root | 有（APatch，`su -c id` → uid=0，但 SELinux 域是 `u:r:shell:s0`） |
| SELinux | **Enforcing**，`setenforce 0` 被拒绝 |
| Zygisk + LSPosed | **实际未生效**（见下） |
| Frida | 已装 frida 17.24.3 + frida-server（arm64，81 MB，`/data/local/tmp/fs`） |

**LSPosed 是空壳，不能直接用**：

```text
/data/adb/modules/zygisk_lsposed/   只有 module.prop + 一个 0 字节的 update
                                    （无 zygisk/、无 system/，module.prop 写的是 v2.2.1 (7912)）
/data/adb/lspd/                     空目录
pm list packages | grep lsposed     无 LSPosed Manager 应用
```

也就是说这个模块只留下了 `module.prop`，实体文件已丢失或从未装全；`/data/adb/modules` 下也没有任何带 `zygisk/` 子目录的模块，`getprop | grep zygisk` 无输出。**当前设备上没有任何可用的 Zygisk 框架**，因此 LSPosed 路线要先重装 Zygisk + LSPosed（需要刷入模块并重启）。

**Frida 走不通**：server 能连上（`frida-ps -U` 能列出进程），但 `frida -U -f` 始终报

```text
Failed to spawn: need Gadget to attach on jailed Android
```

已尝试的绕过与结果：

| 尝试 | 结果 |
| --- | --- |
| 用 `su` 以 root 启动 frida-server（含 `setsid` 脱离 shell） | 仍报 jailed |
| `setenforce 0` | `Permission denied` |
| `magiskpolicy --live --apply` 放行 `allow shell appdomain process *`（含 `ptrace`） | 规则确认写入当前策略（`--print-rules` 可见），**spawn 仍失败** |
| 追加 `allow shell self/shell capability *` | 仍失败 |

Gadget 方案需要把 gadget 打进 APK，等于又回到重签名，自相矛盾。**结论：本机现有条件下 frida 无法 spawn 注入。**

### 7.1 LSPosed 模块需要 hook 的三处

| 目标 | 作用 | 期望行为 |
| --- | --- | --- |
| `Lcom/CameraLens;->equals(Ljava/lang/Object;)Z` | 镜头扫描死循环 | 返回 `this === other` |
| `Lpnt;->o(Landroid/hardware/camera2/CameraCharacteristics$Key;)Ljava/lang/Object;` | 缺失 `postRawSensitivityBoostRange` 时抛异常 | 捕获后若 key 匹配，返回 `Range.create(100,100)` |
| `Lcom/a;->loadConfinesExposureISO()V` | 直读该 key 导致空指针 | 若上一处已兜住，可能无需再 hook；保留为兜底 |

### 7.2 构建模块所需的工具链（本机网络已确认可达）

- `android.jar`：可直接用设备上的 `/system/framework/framework.jar`（含完整 framework 类）作为 javac 的 classpath
- LSPosed/Xposed API：`de.robv.android.xposed:api`（Maven Central 有旧版，接口稳定）
- `d8`：`com.android.tools:r8`（Maven Central）
- `aapt2`：`com.android.tools.build:aapt2`（Maven Central，含 linux 二进制）
- 签名：已有 `apksig-8.7.3.jar` + `gcam-test.p12`
- 已验证可达：`github.com` 200、`pypi.org` 200、`dl.google.com` 200、`repo1.maven.org` 200

模块本身很小：一个 `IXposedHookLoadPackage` 实现 + `assets/xposed_init` + manifest 里的 `xposedmodule` 元数据。

## 8. 下一步计划（按顺序）

前置条件：**LSPosed 必须先真正装上**（当前只是空壳），这一步要刷模块并重启设备。

1. **重装 Zygisk + LSPosed**：下载 LSPosed 的 zygisk 版本 zip，解到 `/data/adb/modules/`（或通过 APatch 的模块安装入口），重启；确认 `/data/adb/lspd/` 下出现 `config/`、`log/` 等目录，并装 LSPosed Manager。
2. **搭模块构建链**：aapt2 + d8 + `framework.jar` + Xposed api → 产出可安装的 LSPosed 模块 APK。若拿不到官方 `api.jar`，可自写同签名 stub（只需 `IXposedHookLoadPackage`、`XC_LoadPackage.LoadPackageParam`、`XposedHelpers`、`XC_MethodHook`、`XposedBridge` 这几个）。
3. **装回 BSG 原版 APK**（保持原始签名，原生层完好），在 LSPosed 里启用模块并勾选 `com.android.MGC_9_6_080`。
4. **验证三处 hook 生效**：`Cancelling viewfinder` 消失、`No implementation found` 保持 0、`viewfinder_frame` 里出现 SurfaceView。
5. 若取景器建立 → 验证快门能否出片 → 再谈 HDR+ 开关是否真正生效。
6. 若 LSPosed 路线也不成，退到 8.x：先修 8.1 的 `nww.h` 空指针（`nww` 是 device_key 解析器，`h(String)` 内部对 `p0` 直接 `toUpperCase`，参数为 null 即崩），至少确认"本机能否跑通 GCam 预览"。

### 8.1 关于期望值的说明

必须说明：即便三处 hook 全部生效，**也只解决了"能启动、能建取景器"**。9.6 在 Android 11 上还存在 API 31 缺口（`View.clearViewTranslationCallback`），YUV HDR+ 是否真能合成、画质是否可接受，都还没有任何证据。**在拿到实拍样张前，不应把任何版本视为适配成功。**

### 8.2 如果决定不再投入

替代方案只有两条：一是接受本机原厂相机；二是用 Camera Go（有 HDR，但与完整版 HDR+ 不是同一管线，不能当作"移植成功"）。
