# 第三十四阶段：分组包围曝光实验

2026-10-30，Asia/Shanghai。根据 Camera2 请求与实际结果错位证据，尝试为曝光切换留出连续帧稳定时间。

从当前真实曝光/增益构造 9 帧同曝光基础计划，然后在 BeginPayloadFrames 前改为：前 3 帧短曝光，后 6 帧 2×长曝光，保持模拟增益相同。长帧使用原生 kBracketedExp 类型。此计划同时供 native 与 Camera2 请求构建读取，不改 CaptureResult 或 FrameMetadata、不绕过一致性校验。仅对短曝光≤50ms 的本次室内测试启用，长曝光≤100ms。GCam 的基准帧覆盖逻辑保持原样。

过渡阶段的长曝光请求可能返回旧短曝光，原生仍可自行丢弃这些帧；目标是后续连续长段能收到稳定的长曝光，同时首段短曝光与预览保持一致。并不宣称固定丢弃 3 帧即可适配所有场景。

所有其它本轮功能削减实验关闭，Blueline、Google AWB=0。该方案默认关闭、结果待补，不属于此前已验证的 6 帧兼容版本。

## 首版结果与修正

首版在 BeginPayloadFrames 前才修改原生请求向量，确认原生计划为 3×20ms + 6×40ms，但 Camera2 实际提交仍是 9×20ms。说明 Java 的拍摄描述已提前从原计划生成，首版并未同时改变两层计划，撤回上文对两层同步的预期。首张保存、13.96 秒快门短暂恢复，之后第二张前又无法就绪，不能视为有效修复或真实包围曝光。

第二版提前到 Gcam_BuildPayloadBurstSpec 返回时修改，使用临时非拥有者 BurstSpec 视图读取/设置原生向量，不新增原生对象所有权、不释放原对象。改为 8 帧（前 3 短，后 5 长），减少资源负担；后续以实际 Camera2 请求与真实结果两层日志验证，不只看原生计划。

## 提前修改的 8 帧版本：最新结果（交接前）

`enhanced-grouped8-early.json`：3/3 保存，快门恢复分别为 10.86、11.06、10.85 秒，同一 PID 14811。nativeAddPayloadFrame 各张接受 8 帧、拒绝 0 帧。当前安装的正是该实验构建，未进行关闭诊断后的回归、额外冷启动与画质检查，未替代第二十六阶段正式 APK。

这三张不能一概写成三次真实包围曝光：

1. shot=0：计划 3×20ms + 5×40ms；Camera2 也实际提交该序列。实际返回曝光为 [20,20,20,20,20,40,40,40] ms，ISO 163/162。已经同时收到真实短/长曝光，并输出 JPEG。
2. shot=1：短段基准升到 40ms，计划 3×40ms + 5×80ms。审计可见实际 [40,40,缺失,40,40,40,40,80] ms；index=2 的 audit-actual 行缺失，不能补造，其它原生接收日志总数为 8。确认至少收到一个 80ms 长曝光并出图。
3. shot=2：输入基准继续升到 80ms，超过 GroupedExposureRepair 的 ≤50ms 条件，分组补丁没有执行；8 个请求和结果均为 80ms。这是同曝光回退，不是第三次包围曝光成功。

连续曝光基准出现 20→40→80ms 的上升，需要优先解决。可能读取了上次长曝光作为下一张的计量输入，也可能预览 AE 未及时恢复；原因尚未证实。不能凭三张 JPEG 宣布完整 HDR+ 增强修复。建议下一阶段记录真实预览 AE 请求/结果、锁定状态和时间戳，再决定如何生成下一张短曝光基准。

目前只确认真实多曝光帧到达原生处理和最终图输出，未测逐帧融合权重，未量化画质/动态范围收益。最新三张尚未拉取做独立像素/色偏 QA。
